# Grants App — implementation plan

## Goal and boundaries

Build the demonstration-only grant intake assistant and staff copilot described in `intent.md` and `spec.md`. Use fictional applicants and a clearly labelled fictional policy. Staff alone make final decisions. Keep the implementation small: one Python application, two static HTML pages, configuration/prompt files, and a dependency image; do not add payments, uploads, notifications, appeals, or multiple programs.

## 1. Prepare the application and policy files

- Create `app.py`, `index.html`, `admin.html`, a dependency list and a minimal container image definition. The container runs `python /mnt/grants/app.py`; the image supplies Python and dependencies, while the mounted share supplies the application and content files. Listen on `0.0.0.0`, default port 8080.
- Include `aiohttp`, an asynchronous PostgreSQL driver, Azure identity/model client dependencies and LangGraph. Keep backend routes, shared services, startup DDL and graphs in `app.py`; avoid a frontend build and a migration framework.
- Add mounted policy, rubric and agent-instruction files. Give policy and rubric explicit versions and machine-readable field definitions, rules and policy section labels. Label the sample grant and its currency fictional. Define the five fields and validation from the specification, including the income threshold of 2000 and the residency rule. The rubric must cite policy sections and distinguish supplied facts, uncertainty and findings.
- Load settings from the environment, including `PORT`, `APP_DIR`, `POLICY_PATH`, `RUBRIC_PATH`, `INSTRUCTIONS_PATH`, PostgreSQL host/database/user, Foundry endpoint/deployment and optional `AZURE_CLIENT_ID`. Validate policy and rubric content and cross-references before use. Missing or invalid configuration must yield an actionable configuration error and must not trigger an assessment or pending transition. Keep credentials and tokens out of these files.

## 2. Establish identity, security and persistence

- Configure Container Apps built-in Entra authentication and HTTPS-only access. Read the platform-injected principal only behind that middleware; derive the stable tenant ID and object ID from claims and reject requests missing either. Upsert separate citizen or staff records on first use of the corresponding portal, refreshing name and email when available. Resolve portal context explicitly for `/api/me` and other shared endpoints.
- Apply the specified demo authorization: accepted users can enter either portal and thereby become staff, but every citizen data access, chat operation and agent tool must enforce ownership, and every staff operation must establish staff context. Ignore client-provided identity and owner IDs. Display the warning that this self-provisioning rule is unsafe for real data and restrict the pilot to controlled accounts.
- Protect cookie-authenticated writes with a same-origin `Origin` check and a CSRF token. For the single-replica MVP, use a server-side session bound to the authenticated principal, a secure HttpOnly session cookie, and a token returned to the UI through `/api/me`; invalidate/reissue sessions after restart or identity change. Require the token on each state-changing API request. Provide `/.auth/logout` links.
- Open PostgreSQL connections over TLS with certificate validation, using a fresh Entra token for `https://ossrdbms-aad.database.windows.net/.default` when opening each connection. Use the same managed identity for routes and agent services. Initialize the six tables and constraints from startup DDL: citizens, staff, applications, messages, assessments and decisions, including UUID keys, identity uniqueness, valid statuses, assessment snapshot uniqueness and one final decision per application. Store UTC timestamps.
- Centralize error handling, request IDs and sanitized operational logging. API failures return the specified JSON envelope and appropriate 400/401/403/404/409/503 status; never log tokens, prompts, conversations or personal data.

## 3. Implement shared application services and HTTP routes

- Build shared, authorization-aware services for policy lookup, application creation/list/detail, partial data validation, field replacement, message persistence, dropping, assessment and staff decisions. Route handlers and narrowly scoped agent tools call these services directly, not one another's HTTP endpoints.
- Implement the routes in the specification: `/api/me`, `/api/policy`, citizen application list/create/detail/save/assess/drop, `/api/chat`, and staff application list/detail/decision. Use JSON and return the current application version after every state change. Citizen detail excludes internal assessment reasoning; staff detail includes the assessment, policy/rubric versions and decision history.
- Create applications as incomplete `submitted` records. Accept only the configured fields, validate supplied values while allowing missing fields, and show missing fields. A confirmed form save replaces the data object only while `submitted`; increment the version for data or status changes. Automatically assess complete saved data; on assessment failure preserve the save, report the failure separately and offer retry. Chat proposals never save field values without form confirmation.
- Enforce the state machine with conditional updates or row locks: owner may drop `submitted` or `pending approval`; staff may approve or reject only `pending approval`, with a non-empty reason and the last observed version. Insert the decision and transition atomically. Reject stale or invalid transitions with 409; terminal records remain read-only. Ensure concurrent drop, assessment and decision operations cannot overwrite one another.
- For assessments, snapshot validated data and its application version before calling the model, without holding a transaction open. Validate output and policy references, then atomically insert the assessment and conditionally transition the same still-submitted version to `pending approval`, incrementing its version. Enforce uniqueness on `(application_id, application_version)`; duplicate or racing requests return an existing result or conflict, not a second assessment. Discard stale output if the application has changed or been dropped.

## 4. Add LangGraph flows

- Build a citizen intake graph with authenticated citizen context, an optional owned application, policy and conversation. Answer policy and process questions, explain that staff decide, identify missing information and return optional structured proposals for the citizen to confirm. Persist citizen and assistant messages only for an owned selected application; general chat can remain transient.
- Build an assessment graph for complete `submitted` snapshots. Supply validated fields, policy and rubric; request structured output with versions, cited rule-by-rule findings, rationale, uncertainties and one of `appears eligible`, `appears ineligible` or `needs review`. Validate the structure, allowed recommendation, versions and references before persistence. Model output never performs a final decision.
- Expose only narrowly scoped policy and authorized-current-application read tools backed by shared services. Treat citizen text as untrusted; do not expose arbitrary files, SQL, other citizens' records or staff/status-changing operations. Use managed-identity Entra tokens for Foundry inference, not an API key. Model or validation failures remain retryable and leave the application `submitted`.

## 5. Build the two AJAX interfaces

- Serve `/` and `/admin` as static HTML with vanilla JavaScript, the exact Bootstrap stylesheet and integrity attributes specified in `spec.md`, and Bootstrap's dark theme. Both pages show identity, demo disclaimer and sign-out.
- Citizen page: policy/process chat even before an application exists; start button; owned application list with status and timestamps; selected application data and conversation; structured form with missing-field indicators and proposed values requiring confirmation; final decision and reason when available. Show assessment progress and retry on failure; allow dropping only eligible states and explain that pending corrections require a new application.
- Staff page: status-filtered queue ordered by latest update, defaulting to `pending approval`; details with identity, fields, conversation, timestamps, assessment and versions, and decision history. Provide approve/reject controls with a required reason only for pending records.
- Send the CSRF token and last observed version for writes. Refresh list and details after writes and on 409. If an assessment response is lost, reload before retrying. Surface saved-data versus assessment failures distinctly and do not expose internal assessment reasoning to citizens.

## 6. Configure and deploy the pilot

- Provision a custom-VNet Container Apps environment, external HTTPS ingress on port 8080 and one replica. Configure Entra app registration, intended account audience, callback URI and Container Apps authentication. Store any required interactive-login client secret as a Container Apps secret, separate from managed identity.
- Configure a managed identity for registry image pull, PostgreSQL and Foundry inference, granting the applicable registry, database/schema and Foundry permissions. Enable PostgreSQL Entra authentication, create the managed identity's database principal through an Entra administrator, and configure database networking and DNS.
- Set up a supported classic NFS Azure file share, private endpoint, private DNS and VNet routing; define Container Apps environment storage and mount it read-only at `/mnt/grants` using `NfsAzureFile`. Restrict share writes to deployment operators. Account for the Container Apps NFS limitation requiring no encryption in transit; NFS access is network-based, not managed-identity data-plane authentication.
- Publish the dependency image to ACR, upload `app.py`, HTML and non-secret configuration/policy/prompt files to the share, set the runtime environment variables, and deploy the container. Update mounted files and restart the revision for application/content changes; rebuild the image when dependencies change.
